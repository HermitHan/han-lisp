# Developing Han

[简体中文](README.zh-CN.md) · [Project overview](../../README.md) · [Making and testing a change](workflow.md) · [Symbol reference](../reference/README.md)

Place a change with the code that owns its data and can interpret its result. Reading a child process's exit status belongs to the host adapter. Choosing a message for that status belongs to the application that ran the command.

## How the system fits together

[han.asd](../../han.asd) loads the runtime serially in the order `test → host → source → os → path → json → args`. The call relationships are more selective. `han.os` delegates process operations to `han.host`, `han.path` delegates filesystem operations to it, and `han.args` can obtain the current argv from it. An explicit argv lets a caller replay an invocation in the REPL. The JSON parser uses recursive descent over a string and integer offsets. Parser authors can use the independent cursor in `han.source` for their own grammars.

Each package declares its exports and provides REPL `help` and `version` functions in `package.lisp`. [han.dev.asd](../../han.dev.asd) separately enumerates the implementation files and module tests and declares a UIOP dependency. Check both ASDF definitions when adding an implementation file. The test framework ships in the runtime. The development system registers the library's test cases.

## Portability boundary

Use one ANSI Common Lisp codebase for the six packages outside `han.host`. Keep reader conditionals, implementation packages and operating-system conventions in the [host adapter](../../host/); the conditionals in the two ASDF manifests select only host files. Standard CL operations can stay with the package that owns their meaning: formatting JSON, joining pathname components, or requesting parent directories before writing a JSON file. Ask two questions when reviewing a change: **who defines the rule, and what can callers rely on?**

| Operation | Shared rule | Host responsibility or observable limit |
| --- | --- | --- |
| JSON and UTF-8 files | [JSON](../../json/core.lisp) owns the ASCII grammar, escapes, surrogate pairs and decimal numbers. [Text readers](../../os/io.lisp) can consume a caller’s open character stream. | [Scalar conversion](../../host/characters.lisp) maps only representable Unicode scalars; invalid escapes or unmappable characters signal `han.json:json-error`. [UTF-8 file I/O](../reference/host/with-open-utf8-file.md) sets the external format; supplied streams keep their own encoding. Malformed file bytes are handled by the stream decoder, not the JSON parser. Floating-point precision and the spelling of a valid number can vary. |
| Executable and shell selection | [han.os](../../os/) determines whether callers receive text, lines, or the process handle. An explicit argv list passes arguments as data. | [Command lookup](../reference/host/find-executable.md) owns the Unix PATH separator, empty entries and fallback directories. Each distinct matching namestring is returned once, in search order. The OS checks execute permission at launch. [Shell argv](../reference/host/shell-command-argv.md) owns shell discovery and `-c`. PATH, installed programs and the behavior of the selected shell can differ. |
| Working directory and pathnames | [han.path](../../path/core.lisp) joins and compares pathname components; a directory represented by a string denotes one absolute component. | A relative path that needs a default base and the internal helper that builds the `*WORKDIR*` binding use the [strict working-directory lookup](../reference/host/working-directory-pathname.md); [cwd](../reference/host/cwd.md) returns a namestring or `nil`. For a logical pathname that would need a parent step, [relative-path](../reference/path/relative-path.md) returns the absolute target. For a named physical file whose explicit `:unspecific` type prevents conversion, retry `namestring` with a missing type. Report an unrepresentable pathname as `file-error`. This rule uses ANSI CL in [han.path](../reference/path/to-namestring.md). Spelling, wildcards and directory contents remain host-dependent. |
| Atomic file replacement | The application decides which entries it may replace, finishes writing the staged file, and protects the entries and their parent directories from competing changes through the switch. | [`atomic-replace-file`](../reference/host/atomic-replace-file.md) takes two literal filename strings. The shared host code checks the type and identity of each existing entry, and the adapter renames the staged file to the exact target in one filesystem operation. Readers can keep reading a previously opened file through the switch. Crash durability requires separate file and directory synchronization. |
| Synchronous commands | With the default capture settings, `han.os:run-program` returns stdout, stderr and exit status as three values, in that order. A nonzero status is returned by default and signals `simple-error` in strict mode (`:ignore-error-status nil`). Failure to launch a program supplied as argv signals an error in either mode. | Han preserves the tool’s ordinary exit code and stderr text. Different systems can produce different codes or diagnostics for the same operation. [Synchronous process contract](../reference/host/run-program-sync.md) |
| Live processes and signals | Wait for the child before reading its final status. Signal termination produces a nonzero status, subject to the same strict-mode rule. | The historical signal convention is the signal number on SBCL and 128 plus that number on LispWorks, ECL and CCL (SIGTERM gives 15 and 143). SBCL, ECL and CCL map an observed stopped state to `:unknown`. LispWorks reports `:running` while no exit code is available. [Exit status](../reference/host/process-exit-code.md) · [Live status](../reference/host/process-status.md) |

At an executable entry point, Han’s internal CLI boundary reports an interrupt and exits with status 1 on SBCL, ECL and CCL. An ordinary error goes to stderr when possible. If stderr itself fails, error reporting ends there. At shutdown, an undelivered stdout result turns success into failure. Retrying a previously handled optional stderr write must preserve success. Delivered LispWorks applications keep the runtime’s own SIGINT notification on stdout and exit with status 1. This concerns the process receiving Ctrl-C. When a parent waits for a child killed by a signal, the child-status convention in the table still applies. [Exit and pending output](../reference/host/quit.md)

A new backend should preserve the existing values, value count and failure behavior wherever it can implement the same operation. Document observable limits on the symbol page and test the guarantee that callers use. The test matrix covers SBCL, LispWorks, Unicode-enabled ECL 26.5.5 and 64-bit Clozure CL (CCL) 1.14 on Apple Silicon macOS and x86-64 Linux. Both ASDF systems select the ECL adapter on Darwin or Linux with the `unicode` feature, and the CCL adapter on those systems with `64-bit-target`. Other builds without a matching adapter use the fallback. Unix file locks call the OS `flock` function directly. [Test workflow](workflow.md#run-the-suite-from-the-checkout) · [Fallback](../../host/unsupported.lisp) · [File lock](../reference/host/call-with-exclusive-file-lock.md)

For synchronous text capture, CCL reads and writes UTF-8. SBCL, LispWorks and ECL read capture files with the implementation’s default external format. A LispWorks image using Latin-1 can therefore decode UTF-8 output as a character per byte. To test a tool’s exact bytes, redirect it to a file and read that file as octets. [Synchronous process I/O](../reference/host/run-program-sync.md)

The ECL adapter uses `posix_spawn` so a launch failure reaches the caller immediately, including when an executable exists but its interpreter is missing. For incoming OS strings it decodes UTF-8 using the number of characters actually read, including across buffer boundaries. It encodes outgoing arguments and environment strings as UTF-8 and gives the child PID to an ECL external-process object for status and waiting. For an explicit working directory, it looks up `posix_spawn_file_actions_addchdir` and its `_np` variant in the system C library. If neither is available, the call signals a launch error. [ECL adapter](../../host/ecl.lisp) · [Process interface](../reference/host/run-program.md)

CCL 1.14 has no working-directory keyword in its Unix process launcher. The CCL adapter uses POSIX spawn actions to set the child directory and connect its file descriptors. Direct execution preserves the supplied program name, UTF-8 arguments and explicit environment. Waiting and status use CCL’s external-process object. [CCL adapter](../../host/ccl.lisp) · [Process handle](../reference/host/host-process-native-handle.md)

LispWorks launches the executable directly through its native process API. With an explicit working directory, the Linux adapter opens the directory and passes its ASCII `/proc/self/fd` path to the native API. This requires read and search permissions on the directory and access to `/proc/self/fd`. On macOS the adapter sets a thread-local directory for the launch and restores the caller’s previous setting as it unwinds. [LispWorks process API](https://www.lispworks.com/documentation/lw81/lw/lw-sys-115.htm) · [Working directory and launch errors](../reference/host/run-program.md)

On macOS and Linux, the LispWorks adapter must start the requested executable in the child’s working directory. For a call with `"./worker"` and `:directory`, place different executables named `worker` in the parent and child directories and assert which one ran. Also check its original `argv[0]`, the environment passed to a native executable, and its PID after launch. A successful exit code alone cannot distinguish two programs. [LispWorks adapter](../../host/lispworks.lisp) · [Process interface](../reference/host/run-program.md)

## What belongs in each package

| Package | Design, source and boundary |
| --- | --- |
| [han.host](../../host/) | A common process handle and function interface wrap native handles. [common.lisp](../../host/common.lisp) prepares synchronous I/O, capture files and cleanup. The [SBCL](../../host/sbcl.lisp), [LispWorks](../../host/lispworks.lisp), [ECL](../../host/ecl.lisp) and [CCL](../../host/ccl.lisp) adapters launch processes, query status and deal with terminals and file descriptors. Start here for an operation that requires an implementation API, and check the [fallback for other implementations](../../host/unsupported.lisp). |
| [han.os](../../os/) | Organizes operations around what a caller needs to get back. [run-shell.lisp](../../os/run-shell.lisp) uses the host-selected shell and returns lines or raw strings. [io.lisp](../../os/io.lisp) owns reading. [env.lisp](../../os/env.lisp) supplies defaults for environment lookups and delegates executable lookup to the host. An individual tool owns its environment variable names and exit policy. |
| [han.path](../../path/core.lisp) | Works with directory components, names, types and relationships between pathnames. `directory-pathname` interprets input as a directory, while `directory-exists-p` probes the filesystem. Add rules for joining or normalizing paths here. Reuse host operations for probing, enumerating and copying real files. |
| [han.source](../../source/char-source.lisp) | Owns character movement and position accounting. Each cursor gets a copy of the input and its own identity. Marks retain index, line and column, and spans hold offsets from a common origin. Check all three coordinates when changing newline handling or rewind. A consuming parser owns quotation, comments and other grammar rules. |
| [han.args](../../args/) | Represents the specification, input and binding result as separately inspectable objects. Lexing recognizes argv shapes, binding interprets them against a specification, and lookup resolves referenced defaults. The application formats diagnostics and supplies any built-in bindings it derives from its environment. See the worked example below for the source files. |
| [han.json](../../json/core.lisp) | The reader and writer share a Lisp representation. Objects use string-keyed hash tables, arrays use vectors, false is `nil`, and null is `:null`. Object lookup preserves presence and the writer sorts object keys. This package signals `json-error` for malformed JSON. A consuming application validates its own required fields. |
| [han.test](../../test/core.lisp) | A dynamically bindable registry holds names and test functions. Redefining a test with the same symbol replaces its registration, which supports iteration at the REPL. Put assertions and runner logic here, and put behavior tests with their owning module, for example in [args/test.lisp](../../args/test.lisp). |

## Trace an argument conflict

Suppose `(--/-n)name=world` takes a single value and a caller supplies `-n Ada --name Lin`. Either spelling works on its own. Only the specification establishes that the two tokens refer to the same option.

| Stage | What happens in this case |
| --- | --- |
| [Specification](../../args/spec.lisp) | `parse-arg-spec` gives the name its short and long entries. `parse-args-spec` collects and validates the command's declarations. |
| [Lexing](../../args/lexer.lisp) | `parse-args-input` separates the command name from argv and retains the original text and positions of the options and their values. |
| [Binding](../../args/bind.lisp) | The binder starts with a copy of the lexer diagnostics. Here the single-value resolver receives two candidates. It produces a binding with status `:conflict` and an error diagnostic with code `:conflict`. |
| [Lookup](../../args/query.lisp) | `get-arg` returns `nil` and `:conflict`. The caller can turn `args-result-diagnostics` into a message or check the code in a test. |

For a new option spelling, first check how the lexer classifies the input. To change how two candidates are resolved, work in the binder. The [development workflow](workflow.md) shows how to replay and test this case.
